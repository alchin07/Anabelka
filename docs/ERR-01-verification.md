# ERR-01 — реализация и результаты проверки

Дата: 26 октября 2026 года. Ветка: `feature/error-display-modes`. Исходная ветка и проверенный HEAD: `feature/category-manager`, `69fe3bcacd64b2d74e7728d6c869d61ee48f0d37`.

## Результат

Реализованы production/development через `app_settings.error_display_mode`, владелец технического доступа — исключительно активная серверная сессия администратора с **ролью owner из БД**. `store_owner` исключён. Настройка и запись аудита сохраняются в одной транзакции. По умолчанию и при сбоях — production.

Встроены существующие ErrorHandler, PublicErrorPage, Router, SystemErrorLog и журнал `storage/logs/app-YYYY-MM-DD.log`. Формат ERR-* сохранён. Режим читается при ошибке или работе с настройками; обычный успешный публичный запрос не читает его. Аварийные чтения и существующие автоматические сповещения не инициализируют таблицы. Новых таблиц/миграций нет.

Разработчик получает только разрешённые поля: HTTP-код, фиксированную безопасную причину, класс именованного исключения, относительный файл/строку при наличии, очищенный маршрут/метод, применимый permission/роль и ссылку ERR-* на защищённую запись. Произвольные сообщения исключений, SQL, trace и переменные запроса в карточку не попадают. Анонимные классы показываются через именованного предка: настоящее имя такого класса может включать абсолютный путь.

Дополнительно обнаружены старые контроллеры, самостоятельно ловящие исключение и печатающие его текст с HTTP 500. Поэтому существующий буфер PublicErrorPage теперь безопасно обрабатывает и такие HTML 5xx. Для уже сформированного JSON 5xx сохраняются объект/массив, ключи, булевы значения, числовые коды и retry-поля; текстовые поля ошибок/секретов очищаются. Обычные 4xx JSON и успешные ответы не переписываются. Отдельного логгера или второго ErrorHandler нет.

Тесты сначала выявляли отсутствие новой функции/небезопасное поведение, затем проходили после реализации. Три замечания независимого ревью исправлены с регрессионной проверкой: сохранение JSON Content-Type, путь в анонимном классе исключения и глобальные настройки логирования тестовой БД. Критических замечаний ревью не выявило.

## Сравнение с контрольным HEAD

Обе версии проверялись в одинаково названных отдельных каталогах `Anabelka`, с одинаковыми PHP/Node/Chromium и правами. Это исключает влияние имени тестового каталога на Router.

| Полный существующий Node-набор | Контрольный HEAD | Новая ветка |
|---|---:|---:|
| Всего | 663 | 665 |
| Пройдено | 394 | 395 |
| Падения | 269 | 269 |
| Пропущено | 0 | 1 |

**Новых имён падающих тестов — 0**, наборы имён с учётом повторов совпали. Полный набор не является зелёным: 190 падений связаны с запретом UNIX sockets при локальном запуске Chromium; ещё 79 уже воспроизведены на исходном HEAD (контракты, PHP/browser-фикстуры и другие ограничения). Это не 269 новых ошибок магазина. Полный поимённый список находится в [ERR-01-existing-failures.txt](ERR-01-existing-failures.txt).

В полном прогоне интеграционный ERR-01-блок явно пропускается без `ERR01_TEST_DSN`, а тест политики проходит. Этот блок отдельно запускался с настоящей MariaDB: 25/25 без пропусков. Два старых статических контракта адаптированы к разрешённой диагностике и новой версии CSS; их проверка публичной безопасности сохранена и дополнена реальными HTTP-тестами.

Команды:

```sh
php tests/error_display_mode_runtime.php
ERR01_TEST_DSN='mysql:host=127.0.0.1;port=3306;dbname=anabelka_err01_test;charset=utf8mb4' \
  node --test --test-reporter=tap tests/error_display_http.test.mjs
node --test --test-reporter=tap tests/public_error_notify_cleanup_contract.test.mjs \
  tests/public_error_privacy_and_zero_badge_contract.test.mjs \
  tests/admin_permission_guard_contract.test.mjs tests/csrf_core_contract.test.mjs
node --test --test-reporter=tap tests/*.test.mjs
```

Учётная запись, порт и база в командах должны принадлежать отдельному тестовому стенду; см. [инструкцию](ERR-01-install-android.md).

## Окружение и границы проверки

Фактически использованы Linux, PHP **8.3.6**, MariaDB **10.11.14**, Node **24**, отдельный облачный Chrome. Синтаксис/SQL написаны с учётом PHP 8.2 и MariaDB 10.4, но это не заменяет запуска целевых версий.

Физические Android 16 / KSWEB PHP 8.2 / MariaDB 10.4 и Windows 11 / XAMPP в этой сессии недоступны. Нативная проверка этих сред остаётся шагом приёмки по инструкции. Проверка media queries не обозначается проверкой реального Android или Windows. Аварийные fixtures не доказывают восстановление после завершения процесса ОС или полного исчерпания ресурсов.

## Решения при реализации

- Полные исходные тексты исключений остаются в защищённом существующем журнале; в карточке использованы безопасные фиксированные сводки. Это намеренно уменьшает детализацию ради исключения утечки секретов.
- Неизвестные/динамические сегменты маршрута скрыты, query удаляется целиком. Это уменьшает детализацию 404, зато не раскрывает токены в пути.
- Нормализация уже пойманных HTML/JSON 5xx добавлена, потому что оставление старого echo текста исключения нарушало бы ERR-01. JSON сохраняет структуру, но небезопасные текстовые поля больше не передаются клиенту.
- Исходный один большой фото-fixture был исключён только из локальной sparse-копии из-за ограничения текстового GitHub API. Его путь/SHA в дереве Git не изменялись; результаты этого фото-эксперимента не выдаются за выполненную проверку изображений.
- Публикация отдельной ветки выполняется по прямому поручению ERR-01. Исходные падения явно зафиксированы, слияние и установка в основной магазин не выполняются.
