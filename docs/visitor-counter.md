# VC-01 · Статистика відвідувань

Модуль рахує **перегляди сторінок**, а не людей. Кожний успішний серверний GET дозволеної HTML-сторінки — один перегляд. Перезавантаження рахується знову; відновлення сторінки з історії без HTTP-запиту — ні. Збір за замовчуванням вимкнений.

## Що зберігається

Єдина таблиця `site_page_view_daily`: дата у часовому поясі сайту, фіксований тип сторінки, фактичний ID об'єкта (або 0) та кількість. Один запит створює один взаємовиключний тип: `home`, `catalog`, `category`, `product`, `news_index`, `news`, `discounts`, `new`.

IP, User-Agent, URL, query string, referrer, UTM, ID користувача/сесії, cookie та відбитки пристроїв у статистику не записуються. Заголовки й шлях тимчасово перевіряються лише для виключення службових запитів. Відвідувачам не додаються аналітичні cookie або localStorage. Звичайні сесії магазину не змінюються і не є ідентифікаторами аналітики.

Виключення: не-GET; не-200; Location/не-HTML; AJAX/JSON; prefetch/prerender/preview; адмін-сесія; localhost, loopback, IP-хости та тестові домени; невідомий хост або інший шлях інсталяції. Немає викликів у API, кошику, замовленнях, пошуку, профілях чи запрошеннях. Мовні параметри, сортування та пагінація не створюють окремих ключів. Запити з токенами/preview також пропускаються.

Власний або успадкований `effective_adult` виключає категорію й товар навіть після підтвердження 18+. У рейтингу додатково перевіряється поточне дерево категорій: старі агрегати не розкривають назви об'єктів, які згодом перенесли в 18+. Загальний перегляд каталогу залишається загальним, без визначення інтересу до 18+.

Роботи відсіюються **евристично** за відомими фрагментами User-Agent (bot, crawler, spider, headless, curl тощо) та ознаками попереднього завантаження. Підроблений User-Agent, невідомий робот або prefetch без відповідних заголовків можуть потрапити в підрахунок. Це не система захисту від накрутки.

## Архітектура й навантаження

Контролери викликають сервіс після виведення дозволеного view. Помилка/виняток під час view, redirect та early return до нього не досягають hook. Сервіс ще раз перевіряє HTTP-контекст, виконується не більше одного разу за запит, не створює схему і не робить зовнішніх HTTP-запитів. Вимкнений або відфільтрований запит не звертається до БД через лічильник.

Запис — один параметризований `INSERT … ON DUPLICATE KEY UPDATE`, без read-modify-write. З'єднання магазину використовується повторно. Відкриті транзакції магазину пропускаються. `SET STATEMENT` обмежує лише цей SQL: max_statement_time=0.1 с, innodb_lock_wait_timeout=1 с, lock_wait_timeout=1 с; налаштування сесії не змінюються. Це best effort: перевищення бюджету, переповнення, відсутня таблиця або інша помилка пропускають перегляд, не зриваючи сторінку. Таймер MariaDB не є жорсткою гарантією часу виконання. Не робляться повторні спроби, запис черги чи персональний журнал помилок.

Первинна документація MariaDB: [SET STATEMENT](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/set-commands/set-statement), [обмеження часу виконання](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/aborting-statements).

## Налаштування

`config/visitor-stats.php` повертає безпечні defaults і читає необов'язковий, git-ignored `config/visitor-stats.local.php`. Зразок — `config/visitor-stats.local.example.php`.

| Ключ | Значення за замовчуванням | Призначення |
| --- | --- | --- |
| enabled | false | Лише справжній boolean true вмикає збір |
| allowed_hosts | [] | Точні нижньорегістрові домени; без wildcard, протоколу або порту |
| base_path | /Anabelka | Шлях саме цієї інсталяції; порожній рядок для кореня домену |
| timezone | Europe/Kyiv | Єдиний пояс для дат, звіту й очищення |
| retention_days | 400 | Налаштовуваний строк зберігання агрегатів |

Forwarded-Host не довіряється. Loopback REMOTE_ADDR виключається навіть з production Host, тому зворотний проксі з loopback-адресою потребує окремого перевіреного налаштування реальної адреси на рівні вебсервера. Не вмикайте збір на тестовій копії й не додавайте її домен у production allowlist. Якщо використовується CDN/full-page cache, сервер рахує тільки запити, що дійшли до PHP; для точного визначення цього MVP такі сторінки мають доходити до PHP.

Адмін-сторінка `/Anabelka/admin/visitor-stats`: сьогодні, вчора, останні 7/30 календарних днів включно із сьогодні; графік і таблиця за 30 днів; топ-10 категорій/товарів за 7/30/90 днів. Порожній звіт і недоступна БД — різні стани. Зміна періоду стосується рейтингів. Браузерна бібліотека графіків не потрібна.

Право `visitor_stats.view` додане до AdminAccess. За стандартним набором воно є у Розробника/Власника, але не у звичайного Адміністратора та менеджерів. Збережені ручні налаштування ролей залишаються пріоритетними: після оновлення перевірте це право у потрібних ролей. Є серверний 403 та повторна перевірка в контролері. Ярлик додається через наявний конструктор, сервіс `visitor_stats`, дублювання заборонене тим самим механізмом. Автоматичного додавання ярлика немає.

## Окрема тестова копія Android / KSWEB

Ці кроки виконуються вручну. Модуль не встановлює себе в основний магазин.

1. Зробіть звичайну ручну резервну копію. Не перемикайте робочу папку «Анабельки» на цю гілку.
2. У Termux створіть новий каталог, наприклад `/storage/emulated/0/htdocs/visitor-counter-test`, і клонуйте в нього підпапку **Anabelka**:

   ```bash
   mkdir -p /storage/emulated/0/htdocs/visitor-counter-test
   git clone --branch feature/visitor-counter --single-branch https://github.com/alchin07/Anabelka.git /storage/emulated/0/htdocs/visitor-counter-test/Anabelka
   ```

3. У phpMyAdmin створіть **нову порожню БД** `anabelka_vc_test`. Для відокремлених автоматичних тестів достатньо цієї БД; робочий дамп не потрібний. Тестова програма створює тільки власні таблиці-фікстури. Ніколи не вказуйте `anabelka` у VC_TEST_DSN.
4. Запустіть PHP 8.2 з PDO MySQL (KSWEB CLI або сумісний PHP у Termux). Перевірте `php -v` і `php -m`. З каталогу тестової копії:

   ```bash
   php tests/visitor_counter_runtime.php
   php tests/visitor_counter_hooks_runtime.php
   php tests/visitor_stats_runtime.php
   export VC_TEST_DSN='mysql:host=127.0.0.1;port=3306;dbname=anabelka_vc_test;charset=utf8mb4'
   export VC_TEST_USER='root'
   export VC_TEST_PASSWORD=''
   php tests/visitor_counter_mariadb.php
   ```

   Порт/обліковий запис мають відповідати тестовій MariaDB KSWEB. Програма перевіряє суфікс `_vc_test` і працює з власними фікстурами. Набір відмовиться запускатися, якщо БД не порожня. Перед повторним запуском створіть ще одну нову порожню БД із суфіксом `_vc_test` або вручну пересоздайте лише цю тестову БД. Тестові фікстури залишаються в ній для огляду; робоча БД не підходить. Якщо CLI немає, не викладайте тести як відкриті HTTP-скрипти; виконайте CLI-перевірку пізніше у відповідному середовищі.
5. Для перевірки **повного інтерфейсу магазину** потрібна окрема повна тестова БД зі схемою магазину, не та фікстурна БД автоматичних тестів. Створіть, наприклад, `anabelka_visitor_ui_test` і відновіть туди перевірену резервну копію/підготовлені тестові дані. У **тестовому** `config/database.php` змініть тільки ім'я БД та тестові реквізити. Не копіюйте цей конфіг назад у робочий проєкт.
6. Додайте в KSWEB окремий host/порт, наприклад 8010, із document root `/storage/emulated/0/htdocs/visitor-counter-test`. Відкривайте `http://127.0.0.1:8010/Anabelka/`. Так наявні посилання `/Anabelka` залишаються всередині тестового сервера. Не підміняйте document root/порт основного магазину.
7. У phpMyAdmin, обравши **тільки тестову UI-БД**, виконайте `database/migrations/2026-10-23_visitor_counter.sql`. Її можна повторити: існуючі агрегати не стираються. Міграція не налаштовує ролі й не змінює інші таблиці.
8. Скопіюйте example-конфіг у `visitor-stats.local.php`, залишивши `enabled => false`. Увійдіть тестовим адміністратором, перевірте право, меню, додавання ярлика, екран без даних і 403 для ролі без права. Тестові перегляди localhost не повинні збільшувати лічильник навіть при enabled=true. Перевірка реального запису виконується CLI-набором із явно змодельованим production-контекстом, без послаблення production-фільтрів.
9. Перевірте 320–430 px, таблицю, довгі назви, 7/30/90 днів, клавіатуру; каталог/товар/18+/пошук/VIP/замовлення/обидва конструктори. Для UI з цифрами використовуйте лише синтетичні агрегати, чітко позначені тестовими. Ніколи не додавайте вигадані дані в основну статистику.

## Windows / XAMPP

Аналогічно створіть окремий checkout, окрему тестову БД й окремий Apache host/порт із батьківським каталогом, усередині якого розміщена `Anabelka`. Приклад CLI — `C:\xampp\php\php.exe`; mysql PDO в XAMPP має бути ввімкнений. Змінні PowerShell задаються як `$env:VC_TEST_DSN='mysql:host=127.0.0.1;port=3306;dbname=anabelka_vc_test;charset=utf8mb4'`; також задайте VC_TEST_USER/VC_TEST_PASSWORD і запустіть той самий PHP-набір. Bash runner призначений для середовища з `mariadbd`/`mariadb-install-db`; на Android/Windows використовуйте явно зазначену нову тестову БД й PHP-набір.

## Зберігання та очищення

За замовчуванням зберігаються суточні агрегати віком до 400 днів; дата cutoff також зберігається, поточний неповний день — додатково. Налаштування `retention_days`: 1–36500. Для обмеження зберігання заплануйте щоденне виконання після перевірки dry-run; автоматичного cron/планувальника ця гілка не встановлює.

```bash
php tools/visitor-stats-prune.php --dry-run
php tools/visitor-stats-prune.php --apply
```

Команда доступна тільки CLI; видаляє виключно рядки `site_page_view_daily`, старші за cutoff у поясі сайту. Один batch — до 1000 найстаріших рядків, максимум 10 batch за запуск (налаштовується `--max-batches=1..100`). Якщо remaining_rows > 0, повторіть після перевірки навантаження. Неправильні timezone/retention відхиляються до з'єднання. `--config=...` і `--database-config=...` дозволяють явно вибрати тестові налаштування. Спершу завжди перевіряйте dry-run і обрану БД. Інші таблиці/фотографії не видаляються.

## Перед публічним увімкненням і відкат

Збір не був увімкнений або розгорнутий у цьому завданні. Перед production окремо перевірте застосовні актуальні вимоги щодо захисту даних та інформування відвідувачів; агрегований формат сам по собі не визначає правову підставу й не є юридичним висновком про відсутність потреби у згоді. Оновіть повідомлення про конфіденційність після такої перевірки. Звичайні webserver access logs і чинний журнал пошуку — окремі системи поза цим модулем.

Швидке вимкнення: enabled=false у local-конфігу. Для відкоту коду поверніть попередню перевірену версію у тестовому checkout; таблиця може залишитися, старий код її не використовує. Не видаляйте таблицю для відкату: це знищить агрегати. Не зливайте гілку та не переносіть у головний магазин без окремого рішення й перевірки пристроїв.
