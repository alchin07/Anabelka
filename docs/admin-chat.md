# Чат адміністраторів «Анабельки»

## Ізоляція
Реалізація знаходиться у новій гілці feature/admin-chat. Гілки main і feature/category-manager не змінено.
Модуль використовує наявні облікові записи admin_users та MariaDB. Для спілкування між Android, Windows та іншими працівниками потрібна **одна інсталяція сервера та спільна база даних**: дві локальні бази не синхронізуються.

## Безпечне встановлення
1. Зробіть ручну повну резервну копію бази даних та файлів.
2. Перевірте нову гілку на тестовій копії.
3. У phpMyAdmin відкрийте базу anabelka та імпортуйте database/migrations/2026-10-21_admin_chat.sql. Він додає лише чотири нові таблиці: admin_chat_conversations, admin_chat_members, admin_chat_messages, admin_chat_attachments; чинні таблиці залишає без змін.
4. Після перевірки перенесіть код із feature/admin-chat до чинної робочої гілки без зміни main.
5. Увійдіть до адмінки та відкрийте /Anabelka/admin/chat, пункт «Чат команди» в меню.
6. Перевірте дозвіл chat.use для ролей. Збережені користувацькі перевизначення ролей можуть вимагати явного додавання дозволу.

## Функції
- Особисті повідомлення; групи з назвою й учасниками, керування членством та перейменування.
- Відповідь, редагування і видалення власного повідомлення, пошук, непрочитані та бейдж.
- До 4 файлів за повідомлення; до 8 МБ кожен. JPEG, PNG, GIF, WebP, PDF, TXT, CSV, ZIP, DOC/DOCX, XLS/XLSX, PPT/PPTX, ODT, ODS.
- Автономний Unicode-пікер емодзі: десятки категорій, пошук, нещодавні. Схожий за призначенням на показане відео, але точне оформлення Viber не копіюється — вигляд залежить від системного шрифту.
- Нові повідомлення перевіряються приблизно кожні 6,5 секунди, коли відкрита сторінка чату. У MVP немає мобільних push, дзвінків, наскрізного шифрування чи голосових повідомлень.

## Безпека та обмеження
- Сесія адміністрування, окреме право chat.use, членство у бесіді на сервері, центральний CSRF на POST.
- SQL-запити параметризовані, текст показується як текст, без HTML.
- Вкладення у storage/admin-chat/ з випадковими назвами, без Git; Apache забороняє прямий HTTP доступ. Завантаження лише через перевірений /admin/chat/file. Для Nginx потрібно окремо закрити цей шлях.
- Через інтернет обов’язково HTTPS. Повідомлення не захищені E2EE: сервер має доступ до їхнього тексту. Вкладення не скануються антивірусом.
- Для максимальної завантаження 8 МБ: PHP fileinfo, upload_max_filesize не менше 8M, post_max_size понад 32M, після налаштувань перезапустити Apache/PHP.

## Перед використанням перевірити
1. Створення особистого чату, групи і додавання/видалення учасника під двома-трьома адмінінами.
2. Повідомлення, відповіді, редагування лише власного тексту, видалення.
3. Прочитання/непрочитання, пошук, емодзі Android/Windows.
4. JPEG, PDF, файл понад 8 МБ, файл .php, відмову у прямому доступі до storage/admin-chat.
5. 403 для іншої ролі без chat.use, для чужої бесіди та відсутнього CSRF.

Синтаксис файлів можна перевірити локально:

    php -l app/Models/AdminChat.php
    php -l app/Controllers/AdminChatController.php
    php -l routes/AdminChat.php
    php -l views/admin/chat/index.php
    node --check js/admin-chat.js
    node --check js/admin-chat-emoji.js
    node --test tests/admin_chat_contract.test.mjs
Зв'язки автора/творця з admin_users використовують ON DELETE SET NULL, щоб не перешкоджати видаленню адміністратора. Історія повідомлень зберігається з підписом «Колишній адміністратор».

## CH-UI-05: статус перегляду

Біля часу власного повідомлення: ✓ «Відправлено» (#86798F), ✓✓ «Переглянуто» (#8A2BE2). У групі при частковому перегляді показано «Переглянули: N із M». M — кількість поточних учасників без автора; якщо M = 0, повного перегляду немає. Додавання або вилучення учасника змінює статус попередніх повідомлень; історичний склад адресатів не зберігається.

Використовується `admin_chat_members.last_read_message_id`, без нових таблиць або міграцій. Історія повертає агреговані `read_status` лише для власних невидалених повідомлень та власну позначку `viewer_read_message_id`. `receipt_from` оновлює старі вихідні статуси й зміни збережених повідомлень/цитат одним пакетним запитом; чужі індивідуальні позначки не передаються. Завантаження історії не позначає її прочитаною.

Клієнт враховує відкриту бесіду, видимість і фокус вкладки, появу вмісту в області переписки, діалоги та переглядач фото. Позначка просувається лише через послідовно переглянуті вхідні повідомлення. При довгій непрочитаній історії відкривається перше непрочитане повідомлення, наступні сторінки підвантажуються під час прокрутки. Невдале підтвердження повторюється; збережена позначка не зменшується. Оновлення галочок не замінює вузли повідомлень/фото або відкритий редактор.

### Окрема перевірка на фізичному Android

Після ручного оновлення **тільки Anabelka-chat-test** відкрити одну спільну тестову інсталяцію під двома-трьома адміністраторами:

1. Надіслати текст, графічний смайлик, фото й PDF; до відкриття одержувачем у автора має бути одна галочка, після появи повідомлення на екрані — дві без перезавантаження (до 6,5 с).
2. У групі з трьома учасниками перевірити 0/2, 1/2, 2/2; вилучити/додати одержувача, залишити одного автора.
3. Згорнути вкладку або перейти до іншої бесіди: нові повідомлення не мають ставати переглянутими. Повторити з відкритим фото та діалогом.
4. У довгій історії перевірити перше непрочитане, поступову прокрутку, стрибок униз через непроглянуту ділянку, відправлення під час непрочитаного хвоста, лічильники непрочитаних.
5. Перевірити фото, масштаб, завантаження, Android Back, документи, серця CH-UI-04; вилучений учасник не отримує історію/статуси/вкладення; POST без CSRF відхиляється.

Автоматизовані браузерні сигнали visibility/focus не замінюють цю перевірку фізичного Android. Робоча інсталяція автоматично не оновлюється.
